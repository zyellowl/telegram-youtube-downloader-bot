## 1. 概述

### 1.1 背景

用户需要一个 Telegram Bot：向 Bot 发送 YouTube 视频链接后，由 Bot 下载视频或音频并把文件传回 Telegram。用户此前已在本机完成过类似项目，但无法在当前工作区找到。

经盘点，完整旧项目位于 `/Users/wsejoy/Documents/ytdl_bot`，具备源代码、测试、README、设计文档、Docker 配置及本地环境配置。当前目标工作区 `/Users/wsejoy/Documents/ChatGPT/telegram_bot` 尚无可运行应用。旧项目虽已通过 32 项离线测试，但用户确认其真实 YouTube 链接下载不准确，常见现象是请求失败、只下载到部分内容、选定清晰度与结果不一致，或独立音视频流没有正确合并。该反馈优先级高于离线测试结果。

本次交付采用“先建立真实样例基线并修复、再迁移验收”的方式，同时保持“旧项目只读保留、目标工作区独立运行”。旧项目只作为恢复和复现依据，不在原地开发，不删除、不覆盖；所有修复、代码交付和后续变更均发生在当前工作区。

### 1.2 产品目标

1. 修复真实 YouTube 链接的解析、格式选择、下载、独立音视频流合并和完整性问题，使回传结果与源媒体及用户选择一致。
2. 对普通视频、Shorts、分享链接、独立音视频流的 720p/1080p 和 MP3 建立可重复的真实端到端验收。
3. 将修复后的代码、测试和运行文档迁移到当前工作区，形成独立、可维护的项目。
4. 在本机通过 Telegram polling 启动 Bot，完成真实链接从提交到 Telegram 文件回传的完整验证。
5. 保留旧项目已有的大文件处理、并发保护、清理、管理员命令及 Docker 能力。
6. 保护 Bot Token 等 secret，不在终端输出、日志、文档、测试结果或版本库中泄露。
7. 明确合法使用边界：仅用于用户有权下载的公开内容，不绕过访问控制。

### 1.3 非目标

- 不开发 Web UI、桌面 UI 或后台管理页面；交互界面仅为 Telegram 对话、命令和内联按钮。
- 不为“技术升级”更换框架或做无关重写；允许为修复真实下载准确性而进行有测试证据的最小必要改动。
- 不接入数据库、Redis、多实例队列、付费、会员、广告或频道订阅验证。
- 不承诺支持 YouTube 以外的网站，不进行无关的竞品模仿或功能扩张。
- 不绕过 DRM、付费墙、登录墙、私密视频、地区限制或其他访问控制。
- 不长期保存下载文件、聊天内容或完整用户历史。
- 不在本轮完成公网服务器部署；Docker 只需随迁移保留并可用于后续部署。

### 1.4 成功指标

- [ ] 目标目录包含可独立安装、测试和启动的项目，运行时不依赖旧目录中的源码。
- [ ] 迁移后原有离线测试在目标目录全部通过，基线不少于 32 项，且 Python 编译检查通过。
- [ ] 旧项目目录内容不因迁移而被修改、删除或覆盖。
- [ ] 本机 Bot 能成功连接 Telegram 并进入 polling；用户可完成“链接 → 格式选择 → 文件回传”的端到端流程。
- [ ] 普通视频、Shorts 和 YouTube 分享链接均能解析到正确的同一源视频，标题与源页面一致。
- [ ] 对含独立音视频流的真实样例，选择 720p 和 1080p 后均能正确下载并合并音视频；结果包含可播放的视频流和音频流，实际高度与所选清晰度一致，禁止静默降级。
- [ ] MP3 真实样例可播放，标题与源一致，音频时长与源视频时长一致；视频与音频完整性允许由容器时间基精度造成的差值不超过 2 秒或源时长的 1%，取较大者。
- [ ] 所有真实样例均从头到尾可播放，没有只下载片段、提前结束、零字节或仅音频/仅视频的错误结果。
- [ ] 真实下载失败时，用户反馈能区分链接解析、格式不可用、下载、合并/转码、完整性校验和 Telegram 上传阶段；管理员日志可通过任务 ID 定位根因且不泄露 secret。
- [ ] 完成或失败的任务会清理独立临时目录，不残留无期限增长的媒体文件。
- [ ] `.env`、Bot Token 及其他 secret 未出现在版本控制、控制台输出、PRD、README 示例或测试快照中。

## 3. 核心用户流程

### 3.1 正常流程

1. 用户向 Bot 发送 `/start` 或 `/help`，获得简短用法及合法使用边界。
2. 用户发送一个 YouTube 公开链接。
3. Bot 校验链接并提示“正在解析”。
4. 解析成功后，Bot 展示与源一致的标题、时长，以及实际可用的 `MP3`、`360p`、`480p`、`720p`、`1080p` 选项。
5. 用户点击一个格式按钮。
6. Bot 检查单用户及全局并发限制，随后提示排队、下载、处理、上传等状态。
7. Bot 使用 `yt-dlp` 下载，必要时使用 `ffmpeg` 合并、提取音频或压缩视频。
8. Bot 在上传前校验产物的视频 ID/标题关联、时长、流类型和实际清晰度，不合格的产物不得发送。
9. Bot 通过 Telegram 将音频、视频或文档发送回当前聊天，并以 Telegram 实际收到的文件作为最终验收对象。
10. Bot 标记完成并清理该任务的临时文件。

### 3.2 大文件流程

- 视频超过普通 Bot API 上传上限时，Bot 按现有策略尝试压缩为可播放 MP4，并控制在配置的上传上限内。
- 非视频文件仍超限时，Bot 按顺序拆分为文档分片并全部发送，同时给出可理解的合并说明。
- 配置 Local Bot API Server 时，可提高单文件上限，但此能力不是本机 MVP 通过的前置条件。

### 3.3 失败流程

- 无效或非目标链接：拒绝创建任务，并提示发送有效的 YouTube 链接。
- 私密、付费、登录受限、地区受限或 DRM 内容：明确说明不支持，不尝试绕过。
- 格式不可用：只展示可用选项，或提示选择更低清晰度/MP3。
- 并发已满：提示排队或稍后重试，不重复创建相同下载任务。
- 下载、转码或上传失败：向用户返回不含敏感实现细节的可操作提示，向管理员日志记录可排障信息。
- 任何失败：释放并发名额并清理该任务产生的临时文件。

## 4. 功能需求

### FR-001：旧项目安全迁移

- **描述**：当执行项目恢复时，系统团队应将旧项目中的应用源码、测试、依赖声明、容器配置和必要文档复制到目标工作区，使目标项目可独立运行，同时保持旧项目不变。
- **优先级**：必须有
- **依赖**：旧项目目录可读；目标工作区可写
- **验收标准**：
  - [ ] AC-1：源码、测试、`pyproject.toml`、README、Dockerfile 和 Compose 配置在目标目录可用。
  - [ ] AC-2：从目标目录安装和运行时，不通过路径引用旧项目源码或资源。
  - [ ] AC-3：迁移前后旧项目关键文件的版本状态或校验无迁移引起的变更。
  - [ ] AC-4：迁移不包含 `.venv`、缓存、下载产物、日志等机器生成文件。
  - [ ] AC-5：旧 `.env` 不被读取或输出；若本机运行需要沿用配置，只允许以不显示内容的本地文件操作完成，并确保目标 `.env` 被 Git 忽略。

### FR-002：命令与使用说明

- **描述**：当用户发送 `/start` 或 `/help` 时，Bot 应返回使用步骤、支持格式、主要限制和合法使用边界。
- **优先级**：必须有
- **依赖**：Telegram handler 注册成功
- **验收标准**：
  - [ ] AC-1：`/start` 返回欢迎信息及“发送 YouTube 链接”的明确下一步。
  - [ ] AC-2：`/help` 说明 MP3 与视频质量、文件大小策略和常见失败原因。
  - [ ] AC-3：文案不声称可绕过私密、付费、登录、地区或 DRM 限制。

### FR-003：链接识别与媒体解析

- **描述**：当用户发送包含一个 YouTube URL 的文本时，Bot 应正确处理普通视频、Shorts、`youtu.be` 及 YouTube 官方分享链接的重定向与查询参数，解析其规范视频 ID 和公开媒体元数据；当链接无效或内容不可访问时，Bot 应拒绝任务并解释原因类别。
- **优先级**：必须有
- **依赖**：`yt-dlp`；网络可访问目标内容
- **验收标准**：
  - [ ] AC-1：支持标准 `youtube.com/watch`、`youtube.com/shorts`、`youtu.be` 短链及 YouTube 官方分享链接；跟随合法重定向后仍绑定正确视频 ID。
  - [ ] AC-2：无有效链接的消息不会触发下载。
  - [ ] AC-3：成功解析后展示的标题、时长、视频 ID 和可选格式与 `yt-dlp` 对该规范链接的当前元数据一致。
  - [ ] AC-4：解析错误不会暴露 Token、代理凭据或完整内部堆栈给普通用户。
  - [ ] AC-5：分享链接中的播放列表、时间戳或跟踪参数不会使 Bot 下载错误视频、整张播放列表或从中间时间点截断内容。

### FR-004：格式选择

- **描述**：当媒体解析成功时，Bot 应通过 Telegram 内联按钮展示 MP3 和实际可用的视频质量，并在用户选择后创建对应任务。
- **优先级**：必须有
- **依赖**：FR-003
- **验收标准**：
  - [ ] AC-1：支持 `MP3`、`360p`、`480p`、`720p`、`1080p` 目标格式。
  - [ ] AC-2：源媒体不具备某清晰度时，不展示可下载按钮；如产品采用降级，必须在下载前明确告知实际目标并由用户确认，禁止静默降级。
  - [ ] AC-3：按钮回调不能通过篡改参数下载未解析或已过期的任意 URL。
  - [ ] AC-4：720p/1080p 选项可正确识别“视频流与音频流分离”的格式组合，按钮含义是最终合并文件的清晰度，而不是仅视频流或错误的相近格式。

### FR-005：下载与媒体处理

- **描述**：当用户选择格式且任务获得执行名额时，Bot 应在独立临时目录中安全调用 `yt-dlp` 下载完整媒体，并在需要时调用 `ffmpeg` 完成音频提取、独立音视频流合并或视频压缩；在上传前必须校验产物而非仅以进程退出码判断成功。
- **优先级**：必须有
- **依赖**：`yt-dlp`、`ffmpeg`、可写下载目录
- **验收标准**：
  - [ ] AC-1：MP3 请求产出可播放的音频文件，标题与源一致，时长与源视频时长差不超过 2 秒或源时长的 1%，取较大者。
  - [ ] AC-2：视频请求产出可被 Telegram 播放或以文档方式接收的完整文件；首尾均可解码，时长与源时长差不超过 2 秒或源时长的 1%，取较大者。
  - [ ] AC-3：用户输入不以拼接 shell 字符串的方式执行；外部程序使用参数数组调用。
  - [ ] AC-4：真实输出路径采用任务 ID 或安全文件名，不信任原始视频标题作为路径。
  - [ ] AC-5：下载、转码失败会转换为明确任务状态，并进入清理流程。
  - [ ] AC-6：对于独立音视频流的 720p/1080p 样例，最终文件同时包含视频流和音频流，实际视频高度等于所选清晰度，且不因格式选择表达式错误退化为低清晰度或仅下载单流。
  - [ ] AC-7：上传前使用媒体探测能力（如 `ffprobe`）校验流类型、时长、分辨率和可读性；空文件、临时分片、未完成扩展名或校验不通过的产物不得发送。

### FR-006：Telegram 文件回传

- **描述**：当媒体处理完成时，Bot 应根据媒体类型与大小使用适合的 Telegram 发送方式，将结果回传到发起请求的聊天。
- **优先级**：必须有
- **依赖**：FR-005；Telegram Bot API
- **验收标准**：
  - [ ] AC-1：音频优先使用音频消息，视频优先使用视频消息，必要时降级为文档。
  - [ ] AC-2：发送目标严格对应任务发起聊天，不发送给其他用户或群组。
  - [ ] AC-3：上传失败时提示更低清晰度、MP3 或稍后重试等可执行方案。
  - [ ] AC-4：上传完成后关闭文件句柄并进入清理流程。

### FR-007：超限压缩与拆分

- **描述**：当输出文件超过 `MAX_UPLOAD_BYTES` 时，若输出为视频，Bot 应按现有策略尝试压缩为可播放 MP4；若非视频仍超限，Bot 应按顺序拆分为可上传的文档分片。
- **优先级**：必须有
- **依赖**：FR-005、FR-006；`ffmpeg`
- **验收标准**：
  - [ ] AC-1：超限视频压缩后的文件不大于配置上限，或在无法达到时给出明确失败提示。
  - [ ] AC-2：非视频分片均不大于配置上限，分片命名含序号与总数且发送顺序正确。
  - [ ] AC-3：Bot 向用户提供 Mac/Linux 可理解的分片合并说明。
  - [ ] AC-4：配置 Local Bot API Server 与更高上限后，未超出新上限的原文件不被不必要地压缩或拆分。

### FR-008：进度和错误反馈

- **描述**：当任务状态变化时，Bot 应向用户呈现解析、排队、下载、处理、上传、完成或失败的当前状态，且不得因高频更新造成 Telegram 限流。
- **优先级**：必须有
- **依赖**：下载服务与 Telegram handler
- **验收标准**：
  - [ ] AC-1：用户提交链接后立即得到已接收或正在解析反馈。
  - [ ] AC-2：长任务至少能区分下载、处理和上传阶段。
  - [ ] AC-3：失败消息包含原因类别、失败阶段和下一步，不向普通用户发送原始 traceback。
  - [ ] AC-4：每个任务生成不含 secret 的短任务 ID；管理员日志用该 ID 关联规范视频 ID、选择格式、实际格式、外部程序退出状态和失败阶段。
  - [ ] AC-5：错误至少区分链接解析、格式不可用、下载网络/源站、音视频合并、转码、完整性校验和 Telegram 上传，避免统一返回“下载失败”。

### FR-009：并发与资源保护

- **描述**：当并发请求达到配置上限时，Bot 应执行每用户任务上限和全局并发上限，避免单一用户或大量任务耗尽本机 CPU、磁盘和带宽。
- **优先级**：必须有
- **依赖**：进程内状态与 `asyncio` 并发控制
- **验收标准**：
  - [ ] AC-1：同一用户的活跃任务数不超过 `MAX_TASKS_PER_USER`。
  - [ ] AC-2：同时执行的下载数不超过 `MAX_CONCURRENT_DOWNLOADS`。
  - [ ] AC-3：任务成功、失败或取消后均释放并发名额。
  - [ ] AC-4：达到上限时用户收到排队或重试提示，而非静默丢失请求。

### FR-010：临时文件清理

- **描述**：当任务完成、失败、取消或文件过期时，Bot 应删除对应临时文件；管理员也可手动触发过期文件清理。
- **优先级**：必须有
- **依赖**：任务目录隔离；清理服务
- **验收标准**：
  - [ ] AC-1：每个任务在独立目录中生成文件，清理不会越过配置的下载根目录。
  - [ ] AC-2：成功与失败路径均有自动清理。
  - [ ] AC-3：`/cleanup` 仅管理员可用，并只清理超过配置寿命的临时内容。
  - [ ] AC-4：清理操作不跟随危险路径删除工作区、用户目录或其他无关文件。

### FR-011：管理员命令

- **描述**：当管理员发送 `/status`、`/cleanup` 或 `/broadcast <text>` 时，Bot 应执行对应管理功能；非管理员调用时应拒绝。
- **优先级**：应该有（旧项目已有，迁移必须保留）
- **依赖**：`ADMIN_USER_IDS` 配置
- **验收标准**：
  - [ ] AC-1：`/status` 返回活跃任务、并发使用情况等非敏感运行状态。
  - [ ] AC-2：`/cleanup` 返回清理结果摘要。
  - [ ] AC-3：`/broadcast` 只发送管理员明确提供的文本，并报告成功/失败数量。
  - [ ] AC-4：任何管理员命令输出都不包含 Bot Token 或环境变量 secret。

### FR-012：本机运行与可选 Docker 运行

- **描述**：当管理员按 README 配置依赖与环境变量时，Bot 应可作为普通 Python 进程在 Mac 上运行；当选择容器方式时，项目应保留可构建的 Docker Compose 配置。
- **优先级**：必须有
- **依赖**：Python 3.12+、`ffmpeg`；Docker 为可选
- **验收标准**：
  - [ ] AC-1：README 给出虚拟环境、依赖安装、配置和 `python -m ytdl_bot` 启动命令。
  - [ ] AC-2：缺失必要配置时进程快速失败并提示变量名，不输出变量值。
  - [ ] AC-3：本机验证不要求 Docker。
  - [ ] AC-4：Dockerfile 与 Compose 配置随迁移保留，下载目录以可控方式挂载。

### FR-013：真实下载准确性回归

- **描述**：当下载实现、`yt-dlp` 版本、格式选择表达式、转码参数或 Telegram 发送策略发生变化时，发布验收必须运行固定的真实公开视频端到端样例集，并对源元数据、下载产物和 Telegram 收件结果进行一致性比对。
- **优先级**：必须有（P0 发布门禁）
- **依赖**：FR-003、FR-004、FR-005、FR-006；真实网络；可公开合法下载的稳定样例；媒体探测工具
- **验收标准**：
  - [ ] AC-1：样例集至少覆盖普通视频 URL、Shorts URL、YouTube 官方分享链接、含独立音视频流的 720p、含独立音视频流的 1080p 和 MP3。
  - [ ] AC-2：每个样例在下载前保存非敏感期望值：规范视频 ID、标题、源时长、目标格式；下载后记录实际标题、时长、流类型和视频高度。
  - [ ] AC-3：普通视频、Shorts 和分享链接下载到正确的视频，不误选列表项、不从时间戳开始截断、不只下载预览片段。
  - [ ] AC-4：720p/1080p 产物同时含音频与视频，实际高度严格等于用户选择；源无该清晰度时必须在下载前明确不可用，不能用较低清晰度冒充成功。
  - [ ] AC-5：MP3 可从头到尾播放；视频和 MP3 标题与源一致，时长差不超过 2 秒或源时长的 1%，取较大者。
  - [ ] AC-6：端到端验收以 Telegram 实际收到的文件为最终产物进行探测，不以下载目录中的中间文件代替。
  - [ ] AC-7：任一必测样例失败、内容不完整、标题错误、时长超差或清晰度错误时，发布门禁失败；32 项离线测试通过不能覆盖该失败。

## 5. 非功能需求

### NFR-001：性能与响应

- **类型**：性能
- **描述**：Bot 不应阻塞 Telegram 事件循环；解析、下载、转码和上传需以异步编排或外部进程方式执行。
- **指标**：在正常网络条件下，收到有效链接后 3 秒内发送解析状态；并发执行数始终不超过配置值；状态更新有节流。

### NFR-002：安全与 secret 管理

- **类型**：安全
- **描述**：Bot Token、代理凭据及其他 secret 只能通过未纳入版本控制的环境配置提供，不得出现在代码、文档示例、日志、测试快照或聊天回复中。
- **指标**：`.gitignore` 覆盖 `.env`；版本库 secret 扫描无命中；错误日志只显示变量名或脱敏值；迁移过程不打印旧 `.env` 内容。

### NFR-003：可靠性与恢复

- **类型**：可靠性
- **描述**：单个任务失败不得导致 Bot 进程退出或并发名额永久占用；外部程序退出成功但产物缺流、截断或不匹配时必须判定为失败。
- **指标**：针对解析失败、下载失败、合并失败、转码失败、完整性校验失败、上传失败和取消的测试均验证释放资源；进程可继续处理下一请求。

### NFR-004：资源与存储

- **类型**：容量
- **描述**：任务必须隔离，临时文件必须有生命周期，限制应可通过环境变量调整。
- **指标**：所有测试任务结束后无孤立临时目录；过期文件可被自动或管理员清理；默认并发与上传限制适合单机保守运行。

### NFR-005：可维护性

- **类型**：工程质量
- **描述**：迁移应保留现有模块边界、类型与测试，不做与恢复目标无关的大规模重构。
- **指标**：目标目录中原有 32 项测试全部通过，并为已复现的真实下载错误增加自动回归测试；`python -m compileall src tests` 通过；README 与实际命令一致。

### NFR-006：隐私

- **类型**：隐私
- **描述**：第一版不使用数据库，不长期保留用户下载历史或媒体；日志只保留排障所需的任务元信息。
- **指标**：默认无持久用户数据库；日志不记录完整媒体内容、Token 或不必要的完整 URL 参数；临时文件按配置清理。

### NFR-007：合规与使用边界

- **类型**：合规
- **描述**：产品仅处理用户有权下载的公开内容，不提供规避内容保护和访问限制的功能。
- **指标**：`/start`、`/help` 和 README 至少一处包含使用边界；受限内容失败时不自动尝试凭据绕过。

### NFR-008：兼容性

- **类型**：兼容性
- **描述**：本机 MVP 面向 macOS、Python 3.12+ 和可用的 `ffmpeg`；部署能力保留 Linux 容器配置。
- **指标**：目标 Mac 上完成本地测试与启动；容器定义通过静态配置检查或构建验证。

### NFR-009：媒体准确性与可诊断性

- **类型**：正确性 / 可观测性
- **描述**：下载结果必须与源媒体及用户选择一致；失败必须能定位到处理阶段和任务，不能将截断、错视频、错清晰度或缺少音频的文件作为成功发送。
- **指标**：真实样例集 100% 通过；标题和规范视频 ID 一致；720p/1080p 实际高度严格匹配选择；产物包含预期流；时长差不超过 2 秒或源时长的 1%，取较大者；每个失败均有任务 ID、阶段、错误分类和脱敏日志。

## 11. 开放问题与默认决策

以下问题不阻塞 MVP，未获得新指示时采用默认决策：

- [ ] **是否限制为仅项目所有者可用？** 默认保留旧项目行为，不新增白名单；若 Bot 对公网公开，再评估准入限制。
- [ ] **默认并发和上传上限是否需针对当前 Mac 调低？** 默认沿用旧项目的保守配置，以真实本机资源验证结果为准微调。
- [ ] **是否立即启用 Local Bot API Server？** 默认不启用；先用 Telegram 云端 Bot API 本机跑通。
- [ ] **是否把 Bot 长期部署到服务器？** 默认不在本轮；本轮只确保 Docker 资产可用并完成本机运行。
